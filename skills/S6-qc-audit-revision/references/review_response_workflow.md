# 审稿闭环协议（Review Response Workflow）

> **用途**：把审稿意见从"一堆待办"变成"**逐条可追溯、可验收**的闭环流程"。
> **配套**：6 份过程文档模板（见 `templates/`）
> **教训来源**：本项目 19 条审稿意见中，17 条闭环、2 条待人工提供信息；整个过程靠这套文档保持可控。

---

## 1. 六份过程文档（标准配置）

| # | 文档 | 作用 | 何时更新 |
|---|---|---|---|
| **01** | 审稿意见处理进度与回查清单 | 总控：每条意见的状态、处理内容、负责人 | 每次处理一条即更新 |
| **02** | 数值审计对照表 | 稿件数字 vs 快照重算 | 数值变更后 |
| **03** | 去重与纳入标准筛查报告 | 重复计数与边界人群疑似清单 | GATE-2/5 裁决时 |
| **04** | EndNote 文献库需修改清单 | 字段级文献修正 | 文献核验后 |
| **05** | 正文引用与库对照表 | 引用链核验 | 投稿前 |
| **06** | 手动插入参考文献详细表 | 逐条插入用完整信息 | 投稿前 |

**为什么要六份**：单份"回复信"无法承载"我改了什么、依据是什么、改到哪一步"。审稿人追问时，过程文档是证据。

## 2. 意见状态机

```
                    ┌──────────────────────────────────────────┐
                    ▼                                          │
  [收到] → NEW ──分派──→ ASSIGNED ──开始处理──→ IN_PROGRESS     │
                                                    │          │
                        ┌───────────────────────────┼──────────┤
                        ▼                           ▼          │
                  NEEDS_HUMAN                   RESOLVED       │
                  （需人工提供信息/决策）         （已处理）      │
                        │                           │          │
                        └── 人提供后回到 IN_PROGRESS ─┘          │
                                                    │          │
                                                    ▼          │
                              VERIFIED（复核通过）→ CLOSED ─────┘
                                                    │
                                                    ▼
                                            DEFERRED（明确不改，须有理由）
```

| 状态 | 含义 | 下一步 |
|---|---|---|
| `NEW` | 刚收到，未分派 | 分派编号与负责人 |
| `ASSIGNED` | 已分派 | 开始处理 |
| `IN_PROGRESS` | 处理中 | 完成或转 `NEEDS_HUMAN` |
| `NEEDS_HUMAN` | ★ 需人工提供信息或决策 | 人响应后回 `IN_PROGRESS` |
| `RESOLVED` | 已处理完 | 进入复核 |
| `VERIFIED` | 复核通过 | → `CLOSED` |
| `CLOSED` | 闭环 | — |
| `DEFERRED` | 明确不改 | **必须写明理由**（如"作者决定不改名"） |

**门禁**：全部意见为 `CLOSED` 或 `DEFERRED` 方可再次投稿。

## 3. 处理单条意见的流程

```
① 拆解：一条意见可能含多个诉求（如"补敏感性分析 + 说明吸收率依据"）
      → 拆成子项，各自编状态
② 分类：属于哪类问题？
      ├─ 数值/事实错误  → 走数值审计协议（02）
      ├─ 方法学补充     → 走敏感性分析协议
      ├─ 数据/纳入问题  → 走去重与筛查协议（03）
      ├─ 文献问题       → 走文献核验协议（04/05/06）
      ├─ 表述/因果表述  → 改写 + 收敛
      └─ 需要新数据     → NEEDS_HUMAN
③ 执行：调对应脚本/流程，产出证据
④ 落稿：更新稿件，并检索**连带需修改的其他位置**（摘要/结论/图注）
⑤ 记录：在 01 文档写处理内容 + 证据位置
⑥ 复核：确认数字可追溯、表述一致 → CLOSED
```

### ③ 拆解示例（本项目实证）

| 原始意见 | 拆解出的子项 | 类型 |
|---|---|---|
| R1-1 血砷 EDI 公式单位错误 | ① 修正公式 ② R 脚本重算 ③ 更新 xlsx ④ 更新 Figure 4 ⑤ 正文加"探索性重建"警示 | 数值 + 图表 + 表述 |
| R3-1 分期不统一 | ① 选定统一方案 ② 改脚本重跑 ③ 更新全部时段标签与数值 ④ 同步 SI | 方法学 + 数值 |
| R3-5 检索式未给全 | ① 补 Table S12 完整检索式 ② 说明是否预先注册 | 补充材料 + 声明 |

## 4. 意见分类与典型处置对照

| 类别 | 典型意见 | 处置 | 常见连带修改 |
|---|---|---|---|
| **公式/单位错误** | "单位不匹配" | 修正公式 → 重算 → 全量数值审计 | 所有下游数值 + 结论 + 图 |
| **数值过时** | "时段 GM 与正文不符" | 数值审计 → 更新 | 趋势描述、降幅百分比、摘要 |
| **分期/口径不一致** | "两处分期不同" | 统一口径 → bump 配置版本 → 重算全流程 | 全部时段标签与数值 |
| **方法学依据缺失** | "0.7 吸收率的依据" | 明确定义为假设 + 敏感性说明 | 方法学 + 局限 |
| **过度推断** | "因果表述不当" | 收敛表述（`drive` → `correlate with`） | 摘要 + Highlights + 讨论 |
| **数据重复计数** | "参与者数是否重复" | 去重筛查 → 措辞修正 | 摘要 + 结果 + 局限 |
| **纳入标准违反** | "是否含职业人群" | 疑似清单 → 人工裁决 → 重算 | 纳入清单 + 全部结果 |
| **引用错配** | "引用与内容不符" | 文献核验 → 全量复查 | 正文引用 + 参考文献表 |
| **更名建议** | "建议改标题为 Meta-analysis" | 人工决策 → `DEFERRED` 或执行 | 标题 + 全文措辞 |
| **需外部信息** | "基金编号" | `NEEDS_HUMAN` | 投稿材料 |

## 5. ★ AI 与人工的边界

### 5.1 AI 可以做的

| 动作 | 说明 |
|---|---|
| 拆解意见为子项 | 一条意见含多诉求时 |
| 分类与分派 | 判定属于哪类问题 |
| 执行脚本产出证据 | 数值审计、去重筛查、敏感性、DOI 核验 |
| 定位连带修改 | 检索摘要/结论/图注中的相关表述 |
| 撰写回复草稿 | 列出"已改什么 + 改在哪 + 依据" |
| 维护状态机 | 更新 01 文档 |

### 5.2 AI 不得做的

| 动作 | 原因 |
|---|---|
| 决定"不改"（`DEFERRED`） | 属作者/导师决策（如本项目"meta-analysis 更名"由作者决定不改） |
| 决定排除某研究 | 领域知识判断（GATE-2） |
| 采信哪个数值 | 数值审计的 `MISMATCH` 裁决（可能是换算问题而非计算问题） |
| 补填外部信息 | 基金编号、注册号、推荐审稿人 |
| 确认"是否预先注册" | 事实性声明 |
| 定稿措辞 | 特别是因果表述的强弱 |
| 删除库记录 | 可能误删唯一副本 |

### 5.3 `NEEDS_HUMAN` 项的标准清单

以下事项**必须在 01 文档中标为 `NEEDS_HUMAN` 并列出**，不得静默跳过：

- [ ] 基金信息 / 项目编号
- [ ] 是否预先注册（PROSPERO 等）及注册号
- [ ] 推荐审稿人
- [ ] CRediT 作者贡献分工
- [ ] AI 使用声明措辞
- [ ] 单位英文名 / 作者英文名拼写
- [ ] 需要新补的数据（如从原文补标砷形态、血基质）
- [ ] 需人裁决的排除名单
- [ ] 账号密码等凭证的处理（★ **不得写入仓库或稿件**）

## 6. 回复信撰写要求

| # | 要求 |
|---|---|
| 1 | **逐条对应**：每条意见一段，标明"意见 → 回应 → 修改位置" |
| 2 | **给出修改位置**：段落号/行号/补充材料表号 |
| 3 | **数值变更要给出新旧值** | 不能只说"已更新" |
| 4 | **不回避**：无法执行的要说明理由（对应 `DEFERRED`） |
| 5 | **新增分析要说明设计**：子集定义、为什么这样做 |
| 6 | **语气中性**：感谢 + 事实 + 修改，不作辩解式表述 |

---

## 7. 闭环检查清单

投稿前逐项确认：

- [ ] 01 文档中**无 `NEW` / `ASSIGNED` / `IN_PROGRESS`** 项
- [ ] 所有 `NEEDS_HUMAN` 已由人响应
- [ ] 所有 `DEFERRED` 都有明确理由
- [ ] 02 数值审计对照表**全部为 `OK`**（或差异已裁决）
- [ ] 03 去重筛查的待裁决项已裁决
- [ ] 04/05/06 文献链核验完成，库与稿一致
- [ ] 稿件数值全部可追溯到快照（无孤儿数字）
- [ ] 摘要 / 结论 / 图注 已同步最新数值
- [ ] 措辞类修改（因果、代表性、计数口径）已在摘要与结论同步
- [ ] 回复信与过程文档**同版本**归档
- [ ] **无凭证类信息**（账号密码等）残留在任何交付文件中

---

## 8. 纪律（六条）

| # | 纪律 |
|---|---|
| 1 | **一条意见可能含多个诉求**，必须拆解，不得当作一条处理 |
| 2 | **处理完必须复核**（`RESOLVED` ≠ `CLOSED`） |
| 3 | **数值变更必须连带检索摘要与结论** |
| 4 | **不改也要写理由**（`DEFERRED` 不是省略） |
| 5 | **过程文档随稿件版本化**，不覆盖旧版 |
| 6 | **AI 只给证据与草稿，结论由人定** |
